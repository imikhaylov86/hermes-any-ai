# AI SDD (Specification Driven Development) Rules

## 1. Spec-First: Спецификация — единственный источник правды
- Каталог `docs/` (`docs/SPEC_INDEX.md` и связанные спеки) определяет, как система ДОЛЖНА работать.
- Код, память ассистента и предположения уступают спецификации.
- Любое архитектурное изменение сначала фиксируется в спеке, и только потом пишется код.

---

## 2. Главный принцип: Non-IT User Mode
**Пользователь — не разработчик.** Он эксперт в продукте, а не в коде.

1. **НЕ задавай пользователю технических вопросов** (например: "Какую библиотеку выбрать?", "Какой тип поля в БД?", "Как назвать таблицу?").
2. **Принимай технические решения сам** по best practice. Если есть выбор — выбирай простейший надежный вариант и кратко поясни в одну строку продуктовыми словами.
3. **Архитектурные вопросы решай через `/architect`**: скажи *"Это архитектурный вопрос. Запустить `/architect`?"* и жди ответа.
4. **Вопросы пользователю — строго в продуктовых терминах**: что делает функция, кто пользователь, какие данные он видит на экране.
5. **Инструкции пользователю**: 1 команда — 1 пункт инструкции. Понятно, конкретно и однозначно, без отсылок к абстрактным рассуждениям.

---

## 3. UI и визуализация обязательны
- Каждая user-facing фича проектируется и реализуется вместе с UI.
- Данные отображаются визуально (графики, списки, таблицы), а не в виде сырого JSON.
- Любые фоновые процессы и задачи отображают свой статус и прогресс на экране приложения.

---

## 4. Роли и нативные Slash-команды
В проекте зарегистрированы 11 стандартных slash-команд в `.agents/skills/`:

| Команда | Назначение | Ключевое правило |
|---|---|---|
| `/bootstrap` | Настройка нового проекта или доменов | Опросник в продуктовых терминах, скелет спеков |
| `/architect` | Проектирование фичи / схемы | НЕ пишет код. Создает и обновляет спеки |
| `/implement` | Написание кода по готовому спеку | Строго по спеку. Backend + UI вместе. Без импровизации |
| `/plan` | Декомпозиция большой задачи | Каждый шаг привязан к спеку и роли |
| `/diagnose` | Поиск корня проблемы (бага) | Root cause, не костыли. Сверка со спеком |
| `/refactor` | Промоут прототипа в чистовой код | Перенос логики из scripts в src + UI по спеку |
| `/review-spec`| Проверка кода и спеков | Чеклист R1-R17, авто-фикс очевидных расхождений |
| `/audit` | Глубокий аудит домена | Полная инвентаризация кода ↔ спеки |
| `/prototype` | Быстрая проверка гипотезы | Скрипты в scripts/_tmp/, проверка внешних API |
| `/operate` | Автономный запуск процессов | Минимум вопросов, отчет в UI и продуктовых терминах |
| `/load-specs` | Загрузка контекста домена | Чтение спеков перед началом работы |

---

## 5. Правила спецификаций (R1–R17)
- **R1** Настоящее время (не "будет сделано", а как работает сейчас/должно работать).
- **R2** Формулы, контракты, схемы (без сырых логов и дампов).
- **R3** Отсутствие дублирования формул и контрактов между спеками.
- **R4** Структура: `§Purpose → §Features → §Decisions → §Gap`.
- **R5** Размер одного спека < 50 KB (при превышении — декомпозиция).
- **R6** Запрещены TODO в теле спека; всё нереализованное выносится в `§Gap`.
- **R7** Устаревшие спеки помечаются `Status: Deprecated → see {new_spec}`.
- **R8** Дополнение существующего спека предпочтительнее создания нового.
- **R14** Change Propagation: при изменении контракта обновляются спеки потребителей.
- **R17** Гигиена `§Gap`: выполненные задачи удаляются из Gap, решения переносятся в `§Decisions`.

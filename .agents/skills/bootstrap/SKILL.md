# Bootstrap Workflow

Первичная настройка нового проекта. Опросник в продуктовых терминах + генерация скелета спеков и кода.

## Когда вызывать

- Один раз, в самом начале нового проекта (после `init.sh`).
- Кит уже скопирован в папку проекта, есть `AGENTS.md`, `skills/`, пустые `docs/`, `src/`, `web/`.
- Цель — **превратить пустой кит в проект с заполненными спеками первого уровня**, готовый для дальнейшей работы через `/architect`.

## ⚠️ Главное (см. AGENTS.md → Non-IT user mode)

- **Все вопросы — в продуктовых терминах.** Никогда не спрашивай "PostgreSQL или SQLite", "FastAPI или Flask", "REST или GraphQL".
- **Технические решения принимай сам по дефолтам кита** (PostgreSQL, FastAPI, React+Vite, APScheduler) — записывай в §Decisions.
- **Опросник — пошаговый.** Один вопрос за раз, жди ответ, потом следующий. Не вали 6 вопросов сразу.
- **Если пользователь не знает ответа** — скажи "ОК, оставлю заглушку, уточним позже через `/architect`" и двигайся дальше. Не блокируйся.

## Процесс

### Шаг 0: Pre-flight setup (молча, без вопросов)

Прежде чем спрашивать пользователя — приведи папку в рабочее состояние. Это нужно когда пользователь скопировал кит руками через Finder, а не через `init.sh`. Если всё уже настроено — пропусти этот шаг, файлы не трогай.

Проверь и сделай (без вопросов пользователю — это не технические решения, а housekeeping):

1. **Sanity check**: убедись что текущая папка — это копия кита. Признаки: есть `skills/bootstrap.md`, `AGENTS.md`, `template/`-style структура (`docs/SPEC_INDEX.md`, `src/`, `web/`, `Makefile`). Если нет — остановись, скажи: "*Эта папка не похожа на проект из стартового кита. Запусти меня в папке, скопированной из `_starter-kit/template/`.*"
2. **`.env`**: если файл `.env` отсутствует, но есть `.env.example` — скопируй: `cp .env.example .env`.
3. **`git init`**: если папки `.git` нет — `git init -q && git config core.hooksPath scripts/hooks`.
4. **pre-push hook**: если `scripts/hooks/pre-push` существует и не executable — `chmod +x scripts/hooks/pre-push`.
5. **`.DS_Store` cleanup**: если в репозитории есть `.DS_Store` файлы (Finder любит их клеить при копировании) — удали через `find . -name .DS_Store -delete`.

Не сообщай пользователю детально что сделал — это рутина. Если что-то реально пришлось менять, скажи одной строкой: "*Подготовил папку: создал .env, инициализировал git.*" и переходи к Шагу 0a.

### Шаг 0a: Приветствие

Скажи пользователю:

> Привет! Я помогу настроить новый проект. Задам несколько простых вопросов о том, **что проект делает**.
> Технические детали я возьму на себя — про PostgreSQL, FastAPI и прочую инфраструктуру думать не нужно.
> Если на какой-то вопрос не знаешь ответа — так и скажи, оставим место для уточнения позже.

### Шаг 1: Имя проекта

> 1️⃣ Как назовём проект? (одно слово, латиницей, маленькими буквами — это будет имя папки и базы данных)

Пример валидных: `crm-tools`, `analytics`, `seo-tools`.

### Шаг 2: Краткое описание

> 2️⃣ Что проект делает? Одна-две фразы простым языком.

Пример: "Считает позиции сайтов в поисковиках и показывает движение по времени" / "Ведёт учёт клиентов и заказов с экспортом в Google Sheets".

### Шаг 3: Пользователь

> 3️⃣ Кто будет пользоваться проектом? (Я / моя команда / клиенты — что-то одно)

### Шаг 4: Основные сущности

> 4️⃣ С какими сущностями работает проект? Перечисли через запятую.
> Пример: "клиенты, заказы, товары" или "ключевые слова, страницы сайта, позиции".

Из этого выведи будущие домены (но не озвучивай это).

### Шаг 5: Внешние сервисы

> 5️⃣ Будет ли проект взаимодействовать с внешними сервисами или API? Например:
> - Google Sheets (читать/писать таблицы)
> - Telegram бот (отправлять уведомления)
> - Какие-то другие API
>
> Можно ответить "пока не знаю" — добавим позже.

Если упомянуты Google Sheets / Telegram — они уже есть в ките (skeleton-ы в `src/services/`). Просто пометь `enabled` в `.env.example`.
Другие API → создай заглушки в `src/services/<service_name>/` с TODO в коде и §Gap в overview.

### Шаг 6: Действия пользователя

> 6️⃣ Что пользователь будет делать в системе? Перечисли 3-7 основных действий.
> Пример: "загружать список ключевых слов, запускать сбор данных, смотреть отчёт по позициям, экспортировать в Excel".

Из этого выведи UI-страницы.

### Шаг 7: Автоматизация

> 7️⃣ Есть ли регулярные задачи, которые должны запускаться по расписанию автоматически?
> Например: "каждую ночь обновлять данные", "раз в неделю отправлять отчёт в Telegram".
> Можно "не знаю / пока нет".

Из этого выведи cron-задачи через APScheduler.

### Шаг 8: Подтверждение плана

После всех ответов сформируй и покажи пользователю:

```
## План настройки проекта "{project_name}"

**Что делает:** {description}

**Домены (модули) которые создам:**
- domain_1: {описание в продуктовых терминах}
- domain_2: {описание}
- ...

**Страницы в интерфейсе:**
- /dashboard — главная (статус, последние запуски, ключевые метрики)
- /<page_1> — {что показывает}
- /<page_2> — {что показывает}
- /tasks — список запусков пайплайнов с прогрессом
- /settings — настройки (токены API, расписание задач)

**Внешние сервисы:**
- {service_1} — {для чего}
- {service_2} — {для чего}

**Автоматические задачи:**
- {task_1} — каждые {период}
- ...

Технические решения которые я приму по умолчанию (изменим позже через /architect если нужно):
- База данных: PostgreSQL (через Docker)
- Backend: FastAPI + APScheduler
- Frontend: React + Vite (страница доступна на http://localhost:3000)
- Аутентификация: пока single-user (login=admin/admin), мульти-юзер позже

Запустить настройку? (да/нет)
```

### Шаг 9: Генерация (после подтверждения)

После "да" — без дальнейших вопросов:

1. **`docs/SPEC_INDEX.md`** — заполни шапку проекта, добавь записи для каждого домена с описанием.
2. **`docs/project_structure.md`** — заполни §2 Domain Map (таблица доменов) и §3 Domain Dependencies (как минимум: api → все домены, домены → core/services).
3. **Для каждого домена создай `docs/<domain>/overview.md`** — по шаблону `docs/_templates/overview.md`. Заполни §1 Purpose, §2 Pipeline (если есть), §3 UI Surface (страницы + действия), §3a Public API (заглушки), §Decisions (D1: технологический стек по дефолтам кита), §Gap (план реализации первого MVP — пронумерованные шаги).
4. **`src/<domain>/__init__.py`** — пустые файлы для каждого домена (структура папок).
5. **`src/services/<service_name>/__init__.py` + skeleton** для упомянутых внешних сервисов (Google Sheets и Telegram уже есть, новые — TODO заглушки).
6. **`web/src/pages/<Page>.tsx`** — заглушки страниц с заголовком и текстом "TODO: реализовать".
7. **`web/src/App.tsx`** — обнови маршруты с упомянутыми страницами.
8. **`.env.example` + `.env`** — заменить `APP_NAME=my-project` на `APP_NAME={project_name}` в обоих файлах. Добавить placeholder'ы для упомянутых внешних API.
9. **`AGENTS.md`** — замени `{{PROJECT_DESCRIPTION}}` на описание проекта, заполни таблицу доменов в §Архитектура.
10. **`README.md`** — заменить `{{PROJECT_NAME}}` на имя проекта и `{{PROJECT_DESCRIPTION}}` на описание. Команды запуска и так в шаблоне (`make up` и т.д.).

### Шаг 10: Финальный отчёт

```
✅ Проект "{name}" настроен.

Создано:
- {N} спеков в docs/
- {M} модулей в src/
- {K} страниц в web/

Следующие шаги:
1. Запусти проект: make up (база данных + backend + frontend в Docker)
2. Открой в браузере http://localhost:3000
3. Зайди в Настройки и вставь токены для {внешних сервисов}

Для разработки первой фичи:
- Выбери любой домен из списка
- Запусти /architect — спроектируем детально
- Потом /implement — напишем код по спеку

Если что-то непонятно — спроси.
```

## Запреты

- НЕ задавай технических вопросов в опросе. Никогда.
- НЕ генерируй сразу production-код. Скелет + §Gap план — достаточно.
- НЕ пропускай шаг подтверждения (Шаг 8) — пользователь должен увидеть план перед генерацией.
- НЕ создавай больше 5-7 доменов. Если пользователь упомянул 10 сущностей — сгруппируй разумно.
- НЕ заполняй §Decisions техническими принятыми решениями без явной пометки "по дефолтам кита, изменимо через /architect".

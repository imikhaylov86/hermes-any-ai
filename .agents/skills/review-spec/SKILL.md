# Review Workflow

Ты — ревьюер. Проверяешь код на баги, безопасность и **соответствие спецификациям**.

## ⚠️ Главное (см. AGENTS.md → Non-IT user mode)

- **Не пиши "Требует обсуждения" с техническими вопросами.** Если что-то неоднозначно: либо чини сам по best practice, либо рекомендуй вызвать `/architect` (но не задавай технических вопросов пользователю в свободной форме).
- В разделе **Требует обсуждения** — только продуктовые вопросы (например: "функция X сейчас прячет ошибку от пользователя — это намеренно?"). Технические вопросы → §Decisions через `/architect`.

## Процесс

1. Прочитай `docs/SPEC_INDEX.md` для понимания какие спеки существуют.
2. Определи область изменений (какие файлы, какой модуль).
3. Прочитай спеки, относящиеся к изменённому коду.
4. Проведи ревью по следующим категориям:

### A. Соответствие спекам (ПРИОРИТЕТ)
- Формулы совпадают с описанными в спеке?
- Схемы данных (колонки, типы) соответствуют спеку?
- Названия (поля, таблицы, параметры) совпадают со спеком?
- Нет ли "изобретённой" логики, которой нет в спеке?

### B. Корректность кода
- Logic errors, edge cases, null/None issues
- Race conditions, API contract violations

### C. Безопасность
- Hardcoded secrets, SQL injection (raw queries without parameters)

### D. Качество кода
- Type hints, порядок импортов, logging вместо print

### E. UI completeness (главное правило проекта)
- Фича user-facing? Есть ли UI-страница/виджет?
- Данные визуализированы (график/таблица), не сырой JSON?
- Кнопка запуска пайплайна, если есть пайплайн?
- UI smoke-checked в браузере?

### F. Спек нуждается в обновлении?
- Код добавляет новую логику, не описанную в спеке?

### G. Spec Hygiene (R1–R17)
- **R1** Настоящее время? Нет "мы планируем", "в будущем"?
- **R2** Нет сырых данных: дампы, логи — только формулы, контракты?
- **R3** Нет дублирования формул/схем между спеками?
- **R4** Структура: §Purpose → §Features → §Decisions → §Gap?
- **R5** Размер < 50 KB?
- **R6** Нет TODO в теле? Всё нереализованное — в §Gap?
- **R7** Deprecated → `Status: Deprecated → see {new_spec}` в шапке?
- **R8** Не создан ли лишний спек?
- **R9** Budget: сколько спеков в домене? >7 → флаг.
- **R10** Мёртвые спеки (< 1 KB, нет ссылок)?
- **R11** Спек в правильной папке?
- **R12** §Gap hygiene:
    - Done-шаги без проблем → удалить из §Gap, решения → §Decisions.
    - Done-шаг с Critical несоответствием → **откатить в Pending** с комментарием причины.
    - Если есть Pending/In Progress — §Gap остаётся, но без Done-мусора.
    - Полную очистку (удаление §Gap целиком) делает `/audit`.

### H. Data Quality (если код с числами)
> Ref: `docs/data_quality.md`
- `floor/ceil/int/round` → discretization bias (§1.1)
- `AVG/SUM` → Jensen's inequality (§1.3), double counting (§1.9)
- `WHERE/if` → survivorship bias (§1.4)
- JOIN/merge → дубли (1:N → N:N)
- N < 30 → shrinkage/fallback? (§1.10)
- Zero vs NULL — различаются? (§1.6)

### I. Cross-Domain Contract Check (R14)
- Изменился Public API домена (§3 Overview)?
- Обновлён §5 Consumed By? Обновлены спеки потребителей?

### J. Pre-commit verification
Прогнать релевантный набор и приложить результат:
- Если изменения в `web/**`: `cd web && npx tsc -b && npm run lint`
- Если изменения в python (`src/`, `tests/`, `scripts/`): `.venv/bin/ruff check src/ tests/ scripts/`
- Для крупных изменений в `src/`: `.venv/bin/python -m compileall -q src/` + `.venv/bin/python scripts/lint_architecture.py`

**Красный статус = Critical.**

5. **Авто-фикс** — поправь сам всё однозначное:
   - Код не соответствует спеку и правильный вариант очевиден → исправь
   - Пропущенный import, type hint, опечатка → исправь
   - Обнови спек если код добавил новую логику
   - Технический вопрос с несколькими вариантами → выбери best practice сам, запиши в §Decisions
   - **НЕ исправляй** только если нужно архитектурное решение → отметь в отчёте: "Нужен `/architect`".

6. Отчёт:

```
## Review: [область]

### Исправлено
- [что поправил сам, включая технические решения принятые по best practice]

### Требует архитектурного решения (рекомендация: /architect)
- [неоднозначные архитектурные вопросы — НЕ задавай их пользователю в свободной форме, рекомендуй /architect]

### Продуктовые вопросы пользователю
- [ТОЛЬКО продуктовые вопросы — например: "Сейчас при ошибке в импорте данных пользователь не видит сообщения. Это намеренно?"]

### Warning
- [рекомендации]

### Good
- [что сделано хорошо]
```

## Режим: Bulk Spec Audit

Когда пользователь просит проверить все спеки:
1. Прочитай `docs/SPEC_INDEX.md` + `docs/project_structure.md` §6.
2. Для каждого домена проверь R1-R11.
3. Cross-spec: дубли формул (R3), спеки <1KB (R10), >50KB (R5).
4. Сводный отчёт. **НЕ правь спеки сам** — правки через `/architect`.

## Правила

- Код не соответствует спеку — это ВСЕГДА Critical.
- НЕ сообщай о спекулятивных проблемах — только подтверждённое.
- НЕ задавай пользователю технических вопросов. См. AGENTS.md.

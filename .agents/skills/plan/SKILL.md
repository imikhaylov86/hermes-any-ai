# Plan Workflow

Ты — планировщик. Разбей задачу на конкретные шаги с привязкой к спекам.

## Главное правило (см. AGENTS.md)

- Технические решения о структуре плана — принимай сам.
- Спрашивай только **продуктовые** уточнения (что должна делать фича, что видит пользователь).
- Каждый шаг проверяй: есть ли в нём UI? Если фича user-facing и UI отсутствует — добавь шаг "UI: страница X / виджет Y".

## Принцип: Constructive Challenge

Не принимай задачу буквально. Перед декомпозицией проверь:
- **Правильная ли цель?** Может решается проще другим путём?
- **Все ли ограничения учтены?** Что пользователь мог упустить?
- **Есть ли альтернативный подход?** Предложи в продуктовых терминах.

Если видишь проблему с постановкой — скажи ДО создания плана.

## Процесс

1. Прочитай `docs/SPEC_INDEX.md`.
2. Уточни **продуктовую** задачу у пользователя если неясно.
3. Прочитай спеки, относящиеся к задаче.
4. Создай план:

```
## План: [Название задачи]

### Шаг 1: [Действие — в продуктовых терминах]
- **Роль:** `/implement` | `/architect`
- **Спеки:** `docs/XX_name.md` (§секция)
- **Что делаем:** [конкретное описание: backend + UI]
- **Результат:** [что увидит пользователь]
- **Зависимости:** нет | Шаг N
```

5. Покажи план пользователю. Спроси одобрение.

## Правила

- **Один шаг = одна логическая единица** (один коммит).
- **Каждый шаг привязан к спеку.** Нет спека → первый шаг: `/architect`.
- **Каждый user-facing шаг включает UI.** Backend без UI = неполный шаг.
- **Укажи роль** для каждого шага.
- **Зависимости явные.**
- **Не более 10 шагов.** Больше → разбей на фазы.

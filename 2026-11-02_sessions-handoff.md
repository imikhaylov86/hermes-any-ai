Симптом: развернулись из бэкапа → в приложении истории сессий нет, но в БД (Room) сессии присутствуют.

2. Исправить так, чтобы после восстановления БД история отображалась без ручных действий.
3. Acceptance: восстановить БД из бэкапа → при открытии приложения истории чатов видны, содержимое сообщений на месте.

## Задача B: ПЕРЕПРОВЕРИТЬ РЕАЛИЗАЦИЮ: сессии чатов не изолированы и теряют контекст

Ожидаемое поведение: каждый чат = отдельная серверная сессия Hermes, контекст сохраняется при перезапуске приложения и не сбрасывается от посторонних действий.

Фактическое (по коду main):
1. **Один глобальный hermesSessionId на всё приложение.** `MobileWebSocketClient.kt` держит `private var hermesSessionId: String?` (строка ~96) — НЕ словарь chatId→serverSessionId. Все чаты шлют промпты через `submitPromptRpc(sid, ...)` в одну серверную сессию.
2. **Перезапуск приложения = новая серверная сессия.** `HermesApp.kt` строки 66–67: `restoreHermesSession(...)` сразу же затирается следующим вызовом `setActiveModel(...)`, который внутри делает `hermesSessionId = null` (MobileWebSocketClient.kt ~784) → onOpen уходит `session.create` вместо resume. Ветка resume мёртвый код; персист в DataStore (`setHermesSessionId`) пишется, но никогда не используется.
3. **Смена модели = новая сессия.** `setActiveModel()` безусловно зануляет hermesSessionId и шлёт `session.create` — даже внутри существующего чата.
4. **Переключение чатов = пересоздание сессии.** `selectSession()` в `ViewModels.kt` (~148) вызывает `resetHermesSession()` → session.create.
5. **Resume без fallback.** Если `hermesSessionId != null` — сразу READY без проверки, что серверная сессия жива; при отказе fallback на session.create отсутствует.

Root-cause: серверная сессия привязана к WS-клиенту (глобальный singleton), а не к чату; плюс конфликт restore→setActiveModel в композиционном руте.

Требования к правке:
1. Хранить маппинг Room-sessionId чата → серверный hermes session_id (персистентно, DataStore/Room-таблица), а не один глобальный var.
2. Убрать зануление hermesSessionId в `setActiveModel` при старте приложения; смена модели НЕ должна рвать серверную сессию (либо явный user-initiated reset).
3. `selectSession` НЕ должен reset'ить серверную сессию — при переключении чата резюмить его серверный sid.
4. При resume: если сервер отвечает «сессия не найдена» — fallback на session.create и обновление маппинга.
5. Для старых чатов без маппинга — однократная привязка, не сброс при каждом открытии.

Acceptance: (а) вопрос в чат → force-stop приложения → открыть — ответ учитывает предыдущий контекст чата; (б) два чата: вопрос в A, переключиться в B, вернуться в A — контекст A не потерян и не подмешан из B; (в) смена модели в чате — контекст сохраняется.
